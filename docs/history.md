# Narrowbit

Local, context-managed coding-agent runtime: **task + repository + durable evidence → the smallest useful active context**. Narrowbit will own task state, memory, verification and model routing while using local or supported provider model adapters.

Goal metric: **correct coding work per unit of AI usage**, not just fewer tokens. If quality drops, Narrowbit has failed.

## Prior handoff (2026-09-30, an independent Codex review found two real release blockers)

**State.** `main` = `fe0f5fd` before this stretch's commit, pushed after. Tests: `npm test` 128, `npm run test:ui` 66, all passing. The user asked Codex (a different model, run independently, no shared context with this session) for a second opinion on public-release readiness. Codex found four issues; all four were independently re-verified against the actual code before any fix — not applied on trust. All four were real.

**1. Verification bypassed command approval (the real severity-1 finding).** `run` actions check `approve` before executing; the agent's `verify` action called `verify()` directly with no approval check at all — and `verify()`'s commands come from the repo's own config (`package.json` scripts, `pyproject.toml`, the new Python detection added 2026-09-29), so an untrusted repo could put anything there and it would run unasked, silently defeating the README's own "commands ask for approval" promise for that one path. **Fixed:** `verify()` gained an optional `approve` callback, checked before each configured command; `runtime.ts`'s agent-invoked `verify` action now passes it through. The CLI's own `narrowbit verify` and the MCP `nb_verify` tool deliberately don't pass one — running verify there is already the user's own direct action, the same trust level as typing `npm test` themselves. A declined check is reported as "declined by user — not run; unconfirmed, not passing," never as a silent pass.

**2. Rewind's `git reset` unstaged the user's own unrelated work.** `restoreCheckpoint` checked out the checkpoint's tree with `git checkout <commit> -- .` then ran a plain `git reset` to leave the result unstaged — but that reset touches the *real* index wholesale, discarding anything the user had staged before restoring, whether or not it had anything to do with the task. **Fixed:** the checkout now goes through a throwaway index (`GIT_INDEX_FILE`, the same trick `snapshotTree()` already uses for taking checkpoints) via `read-tree` + `checkout-index -a -f`, so the real index is never touched and no reset is needed. **Not fixed, disclosed instead:** rewind's "delete anything created since the checkpoint" step still can't distinguish an agent-created file from one the user created independently in the same folder while the task ran — a real limitation of the whole direct-working-tree design, not something patchable in `checkpoints.ts` alone; now documented in the function's own comment rather than left implicit.

**3. `verify()` reported "PASSED" on zero configured checks.** `steps.every(s => s.ok)` on an empty array is vacuously `true`, so a repo with no `verify.test`/`typecheck`/`lint` configured got "VERIFICATION PASSED" despite nothing being checked. **Fixed:** `VerifyResult` gained `ran`; the report now says "NO CHECKS CONFIGURED" and `ok` is `false` when `steps.length === 0`, distinct from a genuine pass. `runtime.ts`'s two places that pattern-matched on `"VERIFICATION FAILED"` text were updated so "no checks" isn't mislabeled as "verification passed" in the router's own summaries.

**4. README overclaimed network privacy.** "The only network calls are to the model provider you choose" ignored the app's own GitHub update check and any connectors the user configures. **Fixed:** reworded to name those explicitly, plus reworded to be precise about what "local-first" actually means (selected code goes to whichever provider you pick, same as typing it into that provider yourself).

**Verification discipline for all four:** re-read the actual code before trusting Codex's line numbers and claims (all four held up); wrote a regression test per fix and confirmed each one actually fails without the fix (`git stash` the fix, re-run, watch it fail, restore) before calling anything done — same discipline as every other fix this project has made. Two new tests added: the verify-approval-gate test and the checkpoint-staged-index test, both directly reproducing the exact failure Codex described.

**5. Follow-up on the click (Python) token gap: one hypothesis disproved, one real bug fixed, the cost gap still unexplained.** The question was whether Python files being invisible to the index (`.py` is kind `other` with no content terms, `CODE_EXT` is JS/TS only, so `search` sees only path words and there are 0 symbols and 0 test links) explains click costing ~3.3× Hono's tokens. **It doesn't:** the 8 click runs made zero `search` calls (only `grep` and `read`), so the index's blindness never came into play. A Python symbol indexer is therefore *not* justified by this evidence and was not built (I had wrongly called it "the one measured gap" before checking the logs). What the logs did show: `detectVerifyPython` configured `mypy .` and `ruff check .` from `pyproject.toml`, but neither is installed in that venv, so every `verify` returned exit 127 and reported FAILED even with all tests green (9 false failures across 8 runs). **Fixed:** `verify()` now treats exit 127 as a skipped check (`skipped: true`, "isn't installed here, did not run, did not pass"), `ok` requires at least one check to have really run, an all-skipped run reports `NO CHECKS RAN`, and the "no tests mapped" pseudo-step counts as skipped too (it previously counted toward a PASS). A genuinely failing check still fails next to a skipped one. Three tests (two fail without the fix). **A/B on the same 8 click tasks, same venv, n=1 each:** false failures 9 → 0, success 6/8 → 7/8, mean tokens 158k → 153k, cost $1.77 → $1.56, Opus steps 40 → 38. Only the false-failure count is a real, mechanism-level effect; the success, token and cost movements are within the run-to-run noise documented elsewhere in this file, and the unchanged Opus-step count means *spurious verify failures were not what drove Opus escalation*. Opus ran in 7 of 8 click runs both times (up to 12 of 20 steps), so why escalation fires so often on click (likely the "2×STALL_THRESHOLD steps with no edit" trigger while reading large files like `core.py`) is the next thing to look at if the Python cost gap matters — read the escalation events before building anything.

**6. Second independent Codex review (after the first round of fixes): one release blocker, one smaller issue, both real and re-verified.** (a) **Rewind deleted the user's own files.** `restoreCheckpoint` unlinked everything present now but absent at the checkpoint — including files the user created themselves in the same folder and *even staged ones* (probe confirmed: a staged new file and an untracked one were both gone; the untracked one unrecoverable). I had documented this as an unfixable limitation last round; Codex was right that documented isn't acceptable for deleted user data, and my own regression test only asserted the file stayed *staged*, never that it still existed on disk. **Fixed by never deleting on a guess:** a staged newer file is left exactly in place; any other newer file is *moved* to `.narrowbit/rewind-trash/<stamp>/<path>` (inside the self-ignored state dir, so it isn't snapshotted or shown as a change) and the result names the folder. The undo still works; a wrong guess now costs a `mv`. `restoreCheckpoint` returns `movedTo`/`kept`. (b) **A task could end plain DONE with edits nothing checked.** When verify reports "no checks", `editedSinceVerify` is (deliberately) cleared so a repo with none configured can still finish — but the result then read as verified. Kept that, and added a separate `checkedSinceEdit` (a verify that really executed, or one of the repo's own verify commands run directly): if edits were applied and none ran, the result summary gets `[Narrowbit: NOT verified — <reason>]` (no verify command configured / no configured check could run / verify not run after the last edit) plus an event; no label for question-only tasks or when a check ran. While doing this: `verify()`'s `ran` now means a check actually *executed*, so a fully declined verify reports NO CHECKS RAN instead of FAILED. Also found earlier by my own CLI walk-through on a clean clone: with no terminal and no `--allow-commands`, verify's checks are (correctly) declined but the run still ended plain DONE — the CLI now prints `note: N command(s) were not run … NOT verified` (covers prompt declines too). All regression tests confirmed to fail without their fix (rewind tests 4-5 with the old `checkpoints.ts`; the two label tests without the runtime change). Process note: two of my own tool calls raced each other this stretch (one chain was stashing files while I started a second build); results from the overlapping run were discarded and everything was re-run serialized — don't run a build/test chain while another that touches `src/` is still in flight.

**7. Does Narrowbit need "vision" (a way to look at what it built)? Tested, not built — no evidence yet that it does.** Narrowbit can already *receive* images (paste/attach a screenshot: Claude via content blocks, Codex via `-i`; sent on the first call only; none for Antigravity). The open question was a self-capture action (headless Chrome `--screenshot`, image sent to the model that turn). Test: six tiny 2-file pages, each with a realistic CSS bug (badge overlapping a title, dialog not centred, long address blowing out a flex row, grid `minmax(1200px…)`, unreadable dark-theme text, misaligned button label), each run twice on Claude via the runtime — **A** with a screenshot attached, **B** text-only with an equally vague prompt ("the dialog doesn't look right") — judged by a hidden layout check measured in headless Chrome (each check verified to FAIL on the buggy page and PASS on a known-good fix before any quota was spent; one bug I'd written, a hyphenated address, didn't actually overflow and was caught this way). **Result: 12/12 pass in both arms, and neither arm ever tried to render the page itself** (0 Chrome/screenshot commands). The screenshot arm cost more, not less: mean 38.2k vs 32.3k tokens/task, $0.185 vs $0.146 over six tasks, with no accuracy gain; step counts were about equal. Fixes were real (`translate(-50%,-50%)`, `align-items:center`, `min-width:0`, fixing the grid width…), with minor unrequested side-effects in both arms (the button icon was shrunk 36→24px in both; the screenshot arm truncated the long address with an ellipsis instead of wrapping it; it also inlined the badge, pushing the card's content down) — the kind of thing a self-look might catch, but the checks don't measure it. **Caveat that limits the conclusion:** these pages are tiny, so reading the CSS reveals the bug and a screenshot adds nothing; the test can't discriminate. It shows vision isn't needed for *easy* CSS fixes, not that it never helps. If it's revisited, use a bigger stylesheet, data-dependent layout or subjective "spacing feels cramped" tasks, and build the `screenshot` action only if the agent then fails or falsely declares done. Kit (generator, hidden checks, runner) is in the session scratchpad, not the repo.

**8. Own security audit (asked by the user after two Codex reviews): found a critical hole both reviews missed — fixed.** **The agent could run any command without approval by editing a file inside `.git/`.** Edits were refused only for `.narrowbit*`; an ordinary `edit` of `.git/config` adding `core.fsmonitor = "<cmd>"` was accepted, and git executed it on the very next git call Narrowbit made itself (the post-edit checkpoint) — reproduced end to end with a stub model, every approval denied, zero prompts, the command ran. Narrowbit runs git constantly, so any repo text that prompt-injects the model could reach it; `.git/hooks/*` and `core.hooksPath` were reachable the same way. **Fixed:** `isGitInternal()` in `runtime.ts` refuses any path with a `.git` segment at any depth and in any letter case (macOS's filesystem treats `.GIT/config` as `.git/config`), checked in `safeAbsPath` on both the spelled path and the *real* path (so a symlink `x -> .git` can't smuggle `x/config` through); read and edit give an explicit "files inside .git are git's own internals" refusal. Reads are refused too (`.git/config` can hold credentials in remote URLs). `.gitignore`, `.github/` and names like `x.git` stay editable. Three tests: the exploit reproduced literally, every spelling (case, new hook, nested repo, symlink, read), and the look-alikes (guarding against over-blocking); both security tests fail without the fix. **Other findings from the same audit, not fixed yet (verified in code, not run):** (a) *approval shows the command, not what it runs* — the agent can rewrite `package.json`'s `"test"` script (edits need no approval) and the user then approves `npm test --silent`, which now runs the agent's code; the edit is visible in the diff, but the approval prompt gives false comfort — consider flagging/confirming edits to script-defining files (`package.json`, `pyproject.toml`, `Makefile`, …) before a matching command runs; (b) *web reader SSRF* — `scripts/crawl4ai_mcp.py` checks the address once, but the headless browser follows redirects and re-resolves DNS, so a public URL redirecting to `169.254.169.254` or a local service gets through (optional connector); (c) *opening a broad folder* (`/`, `/Users`, `~/Documents`) git-inits and commits everything there — only the exact home folder is refused; (d) *opening someone else's repo folder* runs git against its own `.git/config` immediately (a folder from a zip, not a fresh `git clone`, can carry a hostile one) — Narrowbit has no "trust this folder?" step like VS Code's; (e) low: `/api/run` returns a raw 500 if sent attachments with no project open (`attachmentDir(root!)` runs before the guard), and `.narrowbit/rewind-trash/` is never cleaned up. Checked and fine: token + Host check on the local server, page renders untrusted text via `textContent` only (no XSS), Mac shell opens only http(s) links, path escapes incl. symlinks blocked, file reads redacted before reaching the model, connector tokens never sent to the page, attachment names/ids can't traverse, OAuth `state` checked, `.narrowbit/` itself can't be edited.

**9. The rest of the audit's findings, all fixed (user: "fix it, don't go public yet").** (a) **Approval now says when the agent changed what a command runs.** `scriptWarning()` in `runtime.ts`: if this task edited a script-defining file (`package.json`, `pyproject.toml`, `conftest.py`, `Makefile`, `setup.py/.cfg`, `tox.ini`, `justfile`, `Cargo.toml`/`build.rs`, `.npmrc`, …) or a file the command names by whole path word, the approval carries a warning; `RuntimeOptions.approve` is now `(command, warning?)`. The app shows it on the approval card and **re-asks even if the user chose "Allow for this task"** (that permission covered the command as it was); the CLI does the same for "[a]lways", and with `--allow-commands` still prints the warning. Ordinary source edits are deliberately not flagged — running tests on agent-written code is the job, and the diff shows it. (b) **Web reader SSRF closed three ways** (`scripts/crawl4ai_mcp.py`): `follow_redirects()` walks every redirect hop itself and checks each before anything requests it; a Playwright route on the browser context blocks every request the page makes (its own JS, XHR, frames) to a private/local address; the final landed URL is re-checked before text is returned. Proven live against the real crawl4ai: a page whose JS fetched a "secret" from 127.0.0.1 and wrote it into the DOM leaked it without the guard (control) and didn't with it ("Blocked 1 request"). Residual, disclosed in the script: DNS rebinding is only caught by the per-request re-resolution. (c) **Broad folders refused:** `tooBroadForProject()` in `planning.ts` — the disk root, the home folder and its parents, any top-level system folder (`/tmp`, `/Users`…), and top-level home folders (Documents, Desktop, Downloads, Library…) can't be git-init'ed and committed as a project; the test runs with a throwaway HOME so a regression can never touch the real `~/Documents`. (d) **Untrusted repos:** every git call Narrowbit makes now goes through `gitArgs()` (`util.ts`), which adds `-c core.fsmonitor=false` and, for diffs, `--no-ext-diff --no-textconv` — proven: plain `git status` ran a hostile fsmonitor, Narrowbit's calls didn't. Clean/smudge filters can't be switched off without breaking git-lfs/git-crypt (and overriding git-crypt could commit decrypted secrets), so `src/trust.ts` asks before opening a repo whose *local* config defines a non-git-lfs filter program: app → 409 `untrusted` + an in-dialog "Trust and open" (not `window.confirm`); CLI `init`/`agent` → refused with the programs listed, `--trust` accepts; the app won't silently reopen an untrusted last-used repo at launch. Trust is remembered per folder in `~/.narrowbit/trusted-repos.json` keyed to a hash of the filter programs, so a changed program is asked about again. Hooks / `core.hooksPath` are deliberately *not* gated — they only run on commit (the user's own action, standard git behaviour) and husky sets hooksPath in countless repos. (e) Low: `/api/run` with attachments and no project open now returns "open a repository first" instead of a raw 500; `.narrowbit/rewind-trash/` folders older than 14 days are pruned (only folders named like its own timestamps). **Tests:** 7 new unit tests + 2 new end-to-end UI tests; every one confirmed to fail on the pre-fix code. **Process slip:** one of my new UI tests left a jsdom page open, so the UI suite finished but never *exited* and sat for over two hours before I noticed; fixed (page closed in `finally`), and UI runs now go through a hard 5-minute ceiling — always bound a long test run.

## Prior handoff (2026-09-22, strategy update — direction still valid)

**Read all three benchmark records in Status before changing code.** The previous product predicted a context package and injected it into another coding agent. That mechanism failed twice because every fresh session paid the full, uncached injection cost. The on-demand-only MCP arm reached 20.2%, but it is a single noisy run, not a validated product claim.

**Approved direction:** Narrowbit is becoming a provider-independent, context-managed coding-agent runtime. It should plan, explore, edit, run commands, verify, recover, persist work and continue with another model. Its differentiator is a durable, local task state that keeps models from repeatedly reading old conversations, broad repository output and stale evidence.

**Why build a harness:** the original Claude Code sidecar could suggest context and expose MCP tools, but Claude Code retained control of the conversation, tool loop, compaction, delegation and provider session. Narrowbit therefore could not prevent repeated transcript reads, selectively project memory, route routine work to a cheaper model or create a reliable cross-provider handoff. The failed pre-injection runs showed that adding context outside that loop is expensive. An owned harness can control the active model-visible context and measure every automatic action; native Claude Code/Codex/Cursor remain useful integrations and baselines.

**The runtime owns:** an append-only task/evidence log; a bounded active-context projection; Git/worktree state; verification; provider-neutral handoffs; and a per-task token/cost ledger. Raw transcripts, logs, diffs and file excerpts stay local behind retrievable evidence handles. A model receives only the active goal, plan, edits, latest checks, current blocker and evidence relevant to the next action.

**Memory design:** keep four separate stores: working state, full evidence, versioned repository facts/decisions/failures, and routing history. Each durable fact needs provenance, a file hash or Git revision where applicable, confidence and invalidation. Store automatically; inject only on demonstrated relevance. Never recreate predictive pre-injection as default behavior.

**Model policy:** use a Jev-like decision layer to select the smallest capable model, next tool, evidence and retrieval budget. It receives compact metadata (task, paths, signatures, test names, ledger state), never whole source trees by default. Configure model roles such as frontier planner, main executor, cheap explorer/summarizer/verifier and local fallback. Local Decider-2b is the strongest tested offline starting point; hosted Jev is experimental because it breaks local-first.

**Provider boundary:** use officially supported APIs, CLIs, MCP and hooks. Claude Code, Codex and Cursor integrations can remain useful adapters, but their native loops remain theirs. A fully owned Narrowbit runtime needs provider APIs or compatible local endpoints. Do not scrape UIs, extract credentials or rotate accounts to evade service limits.

**Do not start by cloning jcode.** User experience showed jcode could burn quota despite its adaptive grep/memory claims. Feature breadth, automatic memory injection, side agents and swarms are potential token multipliers. Build every automatic feature behind a visible usage ledger and an A/B test.

**Next implementation sequence:** first validate the 20.2% `mcpOnly` signal with a contemporaneous native-vs-mcpOnly repeat. Then build a narrow vertical slice: one owned agent loop, durable task ledger, bounded context projection, on-demand local retrieval, command-output handles and verification. Add one API/local provider, prove successful-task cost, then add routing, handoff and further providers. A usable one-provider slice is roughly 4–6 weeks for one full-time engineer; a credible multi-model runtime is 3–5 months. Equal-success savings remain an experiment, not a promise.

## Prior handoff (2026-09-22, Claude Sonnet 5 → Codex; retained as benchmark history)

**What we were trying to do:** hit the brief's GO bar — ≥40% less effective context than native Claude Code at equal-or-better task success, on a real paired benchmark (n=40, honojs/hono, tasks mined from actual commits with `scripts/build-tasks.mjs --verify-each`). The original design (still the one described lower in this file under "Claude Code integration" and `package.ts`) was **predictive pre-injection**: index the repo, rank files, build a context package, and inject it into the system prompt on every task, alongside 13 `nb_*` MCP tools for on-demand lookups.

**Where it stands: three full 40-task paired runs, verdicts NO-GO / NO-GO / CONTINUE (never GO).** Full numbers for all three are below under "Status" — read those before touching anything. Summary:
1. **Run 1 (predictive injection, full package + protocol text):** 19.1% aggregate token reduction → **NO-GO** (floor is 20%). Fresh (uncached, full-price) tokens were *higher* than native on 39/40 tasks; real dollar cost was higher too. Wins were concentrated in already-cheap cached tokens.
2. **Run 2 (same design, injected content trimmed ~40%):** hypothesis was that the injection was too big. Result was **worse**, not better — 11.2% aggregate, fresh tokens up further, cost up further. This ruled out "verbosity" as the cause.
3. **Run 3 (`BenchArm.mcpOnly` in `src/bench.ts`: injection dropped entirely, only on-demand `nb_*` tools offered, Serena-style):** **20.2%** aggregate → first result to clear the 20% floor (**CONTINUE**, the 20–40% band). Fresh tokens hit near-parity with native (+1.6%, vs +46–56% worse in runs 1–2), and cost dropped for the first time (-12.8%).

**Why it isn't working (the actual mechanism, not a guess):** each benchmark task is a brand-new Claude Code session — nothing is cached across tasks. Anything injected into the system prompt is therefore billed at full, uncached price *every single task*, whether or not the prediction was useful. That fixed tax is bigger than the value of a locally-computed guess, however accurate the ranker is (and the ranker is decent but not great: recall@10 ~97%, hit@1 only 25–72% depending on which reranker is blended in — see the Jev/train/Laya/Decider-2b results below). Dropping the injection and reducing Narrowbit to on-demand tools fixes the fresh-token problem directly, which is exactly what run 3 shows — but that only gets to ~20%, nowhere near 40%, because native Claude Code's own Read/Grep/Glob/Bash loop plus its built-in prompt caching is *already* a fairly efficient baseline. That's one of the brief's own explicit kill criteria ("native harnesses already this efficient"), and the data now supports it.

**Caveats on the one number that isn't a NO-GO:** 20.2% is 0.2 percentage points over the floor, from a single run, with large observed run-to-run variance (one task ranged 476k–1.95M tokens across identical-code reruns the same day), and 16/40 tasks individually used *more* tokens than native. Treat it as "probably real, probably high-teens to low-20s," not a precise, validated figure. **It has not been repeated.**

**What was tried to improve file selection (separate axis, did not address the above):** local weight training (`narrowbit train`, hit@1 25%→60%), hosted Jev reranking (25%→82.5%, breaks local-first), and two local decision-model rerankers, Laya (25%→40%) and Decider-2b (25%→65%, blended with trained weights →72.5%). None of these were wired into the actual benchmarked `buildPackage`/mcpOnly path — they're a parallel research track proving selection *accuracy* isn't the bottleneck; the injection *mechanism* was.

**If continuing this project:** the open, unanswered question is whether 20.2% holds up on a second full run (and ideally a second repo) — that's the next experiment, not a new idea. Beyond that, the ceiling for this architecture looks like the CONTINUE band (20–40%), not GO (≥40%); reaching GO would need either a fundamentally different source of savings (e.g., output/tool-result compression gains, which are implemented in `compress.ts` but not isolated/measured on their own) or accepting that native Claude Code is close to as efficient as a bolt-on local retrieval layer can make it. Do not re-attempt "shrink the injected prompt" — that was tried (run 2) and made things worse, not better. Full task history, exact commands, and every number are in "Status" below; nothing has been changed or reverted after run 3 (`git log`, commit `ad1b6b0`, is current HEAD).

## Product principles (from the brief)

1. Deterministic computation first, AI reasoning second. Use the index, git and parsers for "where is X", "who imports Y", "which tests failed".
2. Local-first. No repo upload, no source telemetry. Secrets never indexed; all emitted text is redacted.
3. Start narrow, expand only on evidence (progressive context loading; `nb_expand`).
4. Every feature needs a benchmark reason to exist. Measure, don't assume.
5. Use only officially supportable integration points (MCP, hooks, CLI flags). No scraping private UIs, patching binaries, or extracting credentials.
6. Provider-independent core; integrations are thin.

**Initial runtime scope:** one owned agent loop, a durable task/evidence ledger, bounded context projection, on-demand local retrieval, safe command-output handles and verification. Add one API or local-compatible provider first. Add model routing and provider handoff only after that vertical slice proves successful-task cost. GUI, cloud coordination, account switching, vector DB/embeddings and agent swarms remain deferred.

**Kill/pivot criteria:** benchmark reduction under ~20%, quality materially worse, native harnesses already this efficient, or users constantly override the selection.

**Go thresholds (n ≥ 30 tasks):** <20% NO-GO, 20–40% CONTINUE, ≥40% GO, ≥60% STRONG GO, all at equal or better success.

## Key design details

- **Ranking signals:** BM25 over identifier sub-words/comments/paths (with morphological expansion), exact and fuzzy symbol names, path and module-name mentions, stack-frame locations, memory-referenced files, git dirty/recency (amplifies existing evidence only; bulk commits ignored), import-graph neighbours, callers of seed symbols, penalties for tests/docs/config/generated. Weights are placeholders to tune against `eval`/`benchmark`.
- **Confidence label** (`high`/`medium`/`low`) is emitted in the package so the agent knows when to treat selection as hints.
- **Token counts are estimates** (chars / 3.6) and labelled "est." everywhere. Benchmarks use provider-reported usage from Claude Code's stream-json output.
- **Memory:** one note per entry in `.narrowbit/memory/<type>s/` (types: fact, decision, constraint, convention, failure, bug, command, environment). Retrieval is deterministic keyword/file overlap; failed approaches get a boost. Legacy JSON memory auto-migrates.
- **Claude Code integration:** `narrowbit claude "<task>"` (appends the package as system prompt + attaches MCP), or `narrowbit install claude` (project `.mcp.json` + `UserPromptSubmit` hook in `.claude/settings.local.json`). The hook never blocks or errors the session; follow-up prompts get only new context.
- **Benchmark isolation:** each task × arm in a fresh worktree at the same commit, `--strict-mcp-config`, alternating arm order. Supports a third "context hygiene" baseline arm (brief §38).
